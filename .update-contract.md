# Updates overhaul: shared contract (all three workers read this)

## What the owner asked for (their words)

"I want you to do an overhaul/improvements of autoupdates. It should be much
easier to auto update things / deal with dev environments with the autoupdate.
I should not have to think about it. I also should have the option to just turn
[on] auto updates so it can just download and restart when it detects a new
one."

The yardstick: after a release is published, a person who turned automatic
updates on does NOTHING and is on the new version within the hour, whatever
kind of install they have, including a development checkout. A person who did
not turn it on gets one clear, one-click offer in one place. Nobody is nagged
about something they cannot act on, and nobody is handed git commands.

The owner's own machine is the hard case and must work: the server runs from a
git checkout (`~/MindFlock/app`, editable install, branch `main`, port 9000,
not the default 8765), with extra packages in its venv that are NOT in
`uv.lock` (so `uv sync` breaks it), and the desktop window is a dev launcher
that leaves dev engines alone. Today, after each release, they `git pull`,
refresh the install metadata by hand (the version shown stays stale otherwise)
and restart by hand.

## How it works today (read the code; this is the map)

- `backend/web/core/self_update.py`: `latest_release()` (GitHub, 15 min cache),
  `install_kind()` = editable | uv-tool | pipx | other, `start_update()` writes
  and runs a detached update script with health check + rollback,
  `editable_update_commands()` only PRINTS git lines (`git checkout <tag>`
  detaches HEAD), `blocked_reason()` refuses editable and other.
- `backend/web/core/update_watch.py`: `tick()` every 5 s restarts onto a
  finished install; `announce()` every 30 min emits `update.available` once per
  release. It never looks at the install kind (a checkout gets nagged), and it
  forgets its marker when GitHub is unreachable (re-announces after a blip).
- `backend/cli_update.py`: `mindflock update` (foreground install, then asks
  the discovered server to restart; with two servers it can restart the wrong
  one).
- `electron/main.js` + `electron/update.js`: own GitHub poll (20 s after
  launch, then every 6 HOURS), `updateEverything({engine, app, auto})`,
  `autoUpdateVerdict` (10 min idle, 2 h cap), setting `autoUpdate` in
  `update-state.json` (default on), toasts.
- `frontend/src/components/settings/screens/Advanced.tsx`: "Version & updates"
  (browser) and `ShellEngineUpdate` (desktop) with the "Install updates
  automatically" switch; `lib/shellUpdate.ts`, `lib/fleet.ts`,
  `EventToasts.tsx`, `NotificationsBell.tsx` for `update.available`.
- There is NO server-side setting for updates and no automatic path outside the
  desktop app.

## The design

### One setting, on the server

`updates.mode` in the server settings: `"auto" | "ask" | "off"`.

- `auto`: when a new version is detected, install it and restart onto it, no
  click.
- `ask`: tell the person once per version, one click installs.
- `off`: do not check, do not announce. A manual "Check now" still works.
- Never chosen (stored blank): effective mode is `ask`. Exception: the desktop
  app migrates its existing `autoUpdate` value once (see Electron below), so a
  desktop user who had automatic updates keeps them.

### Who drives an automatic update

- A desktop app that manages its engine (packaged app, not a dev engine):
  the Electron shell drives, as today (`updateEverything`), because the app
  itself has to update too. The server does not also start one.
- Everything else (uv-tool, pipx, a development checkout, with or without a
  desktop window on top): the SERVER drives, from `update_watch`.
- The server already knows whether a shell is attached (`shell_version` in
  `/api/remote/hello`); the backend worker works out "a shell that manages
  this engine" from what exists and reports it as `managed_by_shell`.

### Development checkout: a real update, not printed commands

For `install_kind() == "editable"`:

- "A new version" means: the checkout is on the repo's default branch (the one
  `origin/HEAD` names, else main/master) and that branch's upstream has commits
  the checkout does not (`behind > 0`). Detect cheaply (compare
  `git ls-remote` with the local remote-tracking ref; fetch only when they
  differ). No GitHub release lookup needed for this, though the release's
  version/notes may still be shown when the new commits include one.
- It can be updated when: on the default branch, no uncommitted changes to
  tracked files, not ahead in a way that stops a fast-forward. The update is:
  `git fetch origin`, `git merge --ff-only`, then refresh the install so the
  reported version is right and any NEW dependency is added, WITHOUT removing
  packages that are not in the lock. Never `uv sync`. (Today's hand recipe is
  `uv pip install -q --python <venv python> --no-deps -e .`; add missing
  dependencies too if you can do it without removals.) Then the same restart
  and health check as the other kinds; if the server does not come back,
  `git reset --hard` is NOT acceptable: move the branch back with
  `git merge --ff-only`'s inverse only if the tree is still clean
  (`git reset --keep <old sha>`), and say what happened.
- When it cannot be updated (another branch, uncommitted changes, diverged): it
  is quiet. No event, no toast, no bell row. The settings screen says in one
  plain line why ("This is a development checkout on branch foo. Updates apply
  when it is on main with nothing uncommitted."). No git commands printed.
- The version a checkout reports must not go stale after a pull.

### Timing of an automatic install (server-driven)

Install as soon as it is detected (it is in the background and disturbs
nothing). The restart keeps every session (they are tmux sessions) and takes
seconds, so: restart at the first moment nobody has typed into any terminal
for 60 s, and in any case after 30 min of waiting. Keep the existing hold for
Setup's install terminal. A failed automatic attempt for a version is not
retried for 6 h, and is reported once (`update.failed`).

### Detection

Server: every 30 min as today, plus on demand. A lookup failure must not
forget what was already announced. Electron: every 30 min instead of 6 h.

## API (backend implements; frontend and Electron consume). Additions only.

`GET /api/update/check?refresh=0|1` keeps every field it has and adds:

```
"mode": "auto" | "ask" | "off",        // effective
"mode_set": true | false,              // false = never chosen
"managed_by_shell": true | false,
"auto": {"active": bool,               // this server will install by itself
         "why": "one plain sentence",  // e.g. "Installs by itself and restarts when you pause."
         "waiting": "" | "typing" | "setup" | "retry_later"},
"dev": null | {                        // only for a development checkout
  "branch": "main", "default_branch": "main",
  "dirty": false, "behind": 3, "ahead": 0,
  "can_update": true,
  "why_not": ""                        // one plain sentence when can_update is false
}
```

For a checkout, `available` is true exactly when `dev.behind > 0 and
dev.can_update`; `blocked` is "" then. `editable_commands` stays in the
payload for old clients but new clients do not show it.

`POST /api/update/mode` body `{"mode": "auto"|"ask"|"off"}` → `{"mode": …}`.
Owner only, like `/api/update/start`. 400 `{"error": …}` on a bad value.

`POST /api/update/start` now also works for a checkout (when
`dev.can_update`). Same response shape. Same `GET /api/update/state` while it
runs.

Events on the shared bus (register them in `backend/web/core/events.py`):

- `update.available` as today, but only when the person can act on it and mode
  is `ask`. New optional field `auto: false`.
- `update.installing` `{version, tag, auto: bool}` when an install starts.
- `update.done` `{version, from_version, auto: bool, notes_url}` once, after the
  server is back on the new version (survives the restart: persist it).
- `update.failed` `{version, error, auto: bool}` once per failed attempt. `error`
  is a plain sentence.

CLI (`backend/cli_update.py`), backend worker:

- `mindflock update` works on a checkout (the same fast-forward path) and
  restarts the server that runs from THIS install (match by install path or
  pid, not by the default port).
- `mindflock update --auto on|off|ask` sets the mode; `mindflock update
  --check` prints what would happen and why, without changing anything.

## Electron (electron worker)

- Check every 30 min (was 6 h).
- The mode comes from the server (`mode` in `/api/update/check`), cached in
  `update-state.json` for when the server is down. One-time migration: when the
  server says `mode_set: false` and `update-state.json` holds an explicit
  `autoUpdate`, POST it (`true → auto`, `false → ask`). When the server answer
  lacks `mode` (an older engine), behave exactly as today.
- IPC kept and still working: `update:set-auto` (it now also POSTs the mode to
  the server). New: `update:get` includes `mode`.
- `mode off`: no checks, no toasts. `ask`: today's toast. `auto`: today's
  automatic path; when the server reports it drives itself
  (`managed_by_shell: false`, e.g. a dev engine), the shell does NOT also show
  an engine toast for it.
- Server on a port other than 8765: every local fetch the update code makes
  must use the port the window is actually on.
- Anything else you find that makes a person think about updates.

## Frontend (frontend worker)

- Settings → Advanced, one "Updates" block, the same in the browser and the
  desktop app: a three-way choice (Automatic / Ask me / Off) bound to
  `POST /api/update/mode` (in the desktop app also call
  `window.mfupdate.setAuto?.(mode === "auto")`), the current version, what is
  available, one button when there is something to install, and one plain line
  of state (`auto.why`, `dev.why_not`). No git commands. A checkout that can
  update gets the same button as everyone else.
- `update.installing`, `update.done`, `update.failed`: one quiet toast each and
  a bell row for done/failed ("Updated to v0.14.22" with a "What's new" link
  when the existing What's new feature can show it). In `auto` mode the person
  sees at most: a brief "Updating…" and the "Updated" line.
- `update.available` only offers when `mode` is `ask`; the toast/bell row gets
  an "Update" button that starts it right there (owner only), not a pointer to
  Settings.
- Feature-detect every new field (an older server has none of them): fall back
  to today's behaviour.

## House rules for every worker

- Repo guide: `AGENTS.md`, `docs/development.md`.
- Electron has no `window.prompt/alert/confirm`: never use them.
- Plain, short UI copy. No emoji. Say "development checkout", not "editable".
- NEVER run an update, a `git pull`, `uv sync`, or a server restart against the
  real machine: not in `/home/emandel2630/MindFlock/app`, not on port 9000 or
  8765, not against `~/.mindflock`. Test with unit tests, temp git repos and
  fakes. Do not start servers.
- Run only the tests that cover what you touched; never `pytest -n auto`.
  Python: `MINDFLOCK_AUTH=0 uv run pytest tests/unit/<files> -q` with
  `CS_WEB_MODE` unset (copy `/home/emandel2630/MindFlock/app/.python-version`
  into your worktree first if it is missing). Frontend: `npx tsc --noEmit` and
  `npm test -- <files>` in `frontend/` (if `node_modules` is missing, symlink
  `/home/emandel2630/MindFlock/app-todo/frontend/node_modules`). Electron:
  `node --test electron/test/` style, as `electron/package.json` says.
- Do NOT run `npm run build`, do not touch `backend/web/static/app.js` or
  `style.css`, do not edit `CHANGELOG.md`: the integrator does those once.
- Code against THIS contract, not another worker's code (you cannot see it).
  If the contract is wrong or missing something, pick the smallest sensible
  answer, do it, and say so plainly in your report.
- Existing tests that pin old behaviour you are deliberately changing: update
  them and say which.
- Commit with `SKIP=run-tests,bump-deps,gitnexus-index git commit -s -m "…"`,
  NO `Co-Authored-By` trailer. No push, no PR, no merge.
- Then `report_result` once: what you built, what you tested (with results),
  what you could not do or decided differently from this contract, and
  anything a person should check by hand.
